# MockCharles 四模块项目规划

日期：2026-09-10。四个一级模块及流量双维度展示由用户本轮明确；下文标注“建议”的行为用于后续评审。当前仓库只有设计文档，没有应用实现。

本文是产品结构的统一入口，替代旧的六工作区和七导航入口规划。技术细节继续见 [详细设计索引](design/README.md)，产品细则统一登记在 [决策登记](design/decisions.md)。

## 1. 四个模块与职责

| 一级模块 | 管理什么 | 主要功能 | 边界 |
| --- | --- | --- | --- |
| 设备管理 | 设备来源 IP 及其实际使用配置 | 证书生成与下载、接入说明、IP 列表、备注、绑定项目与规则集、查看该 IP 流量 | 负责选择配置；不在设备页维护一份私有规则副本 |
| 规则管理 | 可复用的接口规则和 Header 规则 | 匹配条件、固定/随机响应、请求头管理、原有响应头修改、预览、引用查看 | 负责定义单条规则；规则执行顺序由规则集管理 |
| 规则集管理 | 规则组合及编排 | 创建、引用规则、排序、查看关联设备；承接原顺序 Mock 组的步骤编排和运行详情 | 定义可共享，设备运行状态独立；“优先级匹配”和“按步骤执行”明确区分 |
| 流量 | 实际通过本代理的请求与响应 | 全部 IP/单 IP、流式/目录式、过滤、详情、命中解释、从流量创建规则 | 展示实际观察结果；切换视图不改变代理、绑定或规则执行 |

项目仍是配置隔离空间，保留已确认的多项目同时服务、每 IP 同时绑定一个项目。项目选择和应用设置作为公共入口，不增加第五个业务模块。证书操作统一从设备管理进入；监听启停保留在公共状态栏。

## 2. 设备管理

- 接入区：选择电脑局域网地址/端口、手动开启代理、生成及下载 CA 公共证书、展示安装与信任指引。二维码是可选交互建议。
- 设备列表：来源 IP、备注、最近活动、实际绑定项目、当前工作模式、对应规则集；提供“查看此 IP 流量”。没有心跳时用最近活动表达状态，不把没有请求直接判断成离线。
- 绑定区：沿用真实转发、独立 Mock、顺序执行三种已有行为；独立模式选择优先匹配规则集，顺序模式选择顺序编排定义。未绑定/新 IP 真实转发，不自动采用当前查看项目。
- 原顺序运行的开始、停止、重置放在设备上下文内，规则集详情只读查看设备运行并跳转设备页，不提供启动/停止/重置按钮。

证书由本机代理统一管理，下载到多台设备，不按 IP 重复创建一套 CA。下载仅提供公共证书，不提供私钥；生成/重置证书要说明对已安装设备的影响。CA 生命周期及证书下载入口的具体实现见 D21。

IP 是网络来源，不是永久设备身份。IP 变化、IP 被另一台设备复用、NAT 共用 IP 都需要可见提示与手动核对；“移除设备记录”不等于阻止设备再次连接，也不等于删除历史流量。

## 3. 规则管理

建议页面分为“接口规则”和“Header 规则”两个页签。

接口规则保存名称、备注、原始请求匹配条件、固定或随机响应、接口专用 Header。从实际流量创建草稿，编辑、预览、保存，再加入规则集和绑定设备，形成完整闭环。保存一条规则不意味着自动让所有设备使用它。

请求头支持增加、覆盖、删除等操作，具体操作语义沿用 [匹配与 Header 设计](design/04-matching-headers.md)。以前已确认的响应头修改继续保留为方向选项。通用 Header 的编辑入口从项目配置移到这里，作用范围仍由项目和匹配条件限定；命中接口的 Header 在通用规则后应用。

样本库、业务数据集、单记录模板和随机生成能力保留在规则管理的辅助面板/选择器中，不再占一级导航。源数据只在编辑时参与，保存后的响应不依赖运行时查询源记录。

共享规则编辑可能影响多个规则集和设备：编辑器应显示引用关系、保存后的生效提示以及版本冲突。禁用独立 Mock、禁用顺序步骤、关闭流量保存是三个不同操作，不合并成一个含糊的总开关。是否增加规则集成员级开关见 D19，不能默认为已有能力。

## 4. 规则集管理

将两种编排集中在一个模块，先采用两个类型入口的组织建议：

| 类型 | 请求选择规则 | 顺序的含义 | 运行状态 |
| --- | --- | --- | --- |
| 优先匹配（原独立规则集） | 按顺序取第一条启用且匹配规则；未命中真实转发 | 冲突时谁优先，不要求客户端依次请求 | 无步骤游标 |
| 顺序执行（原 Mock 组） | 只判断当前有效步骤；其他请求真实转发 | 客户端业务请求的消费顺序 | 每 IP 独立开始、推进、完成、停止、重置 |

这是入口归并建议，不擅自把现有 rule_sets 与 mock_groups 数据模型合成一张表，也不引入类型自动转换。顺序执行沿用既有确认：完整响应写出成功才推进，失败不推进，结束后真实转发，不回退优先匹配；切出或改绑停止旧运行，新运行手动开始。

规则集编辑只编排引用，不重复维护规则正文。显示被哪些设备使用、规则有效性和修改生效范围。响应修改下一请求生效、在途保留版本；顺序步骤和开关在下次开始/重置采用，其他定义变更时机仍见 D06。

## 5. 流量：两个独立维度

| 查看范围 | 流式 | 目录式 |
| --- | --- | --- |
| 全部 IP | 同一时间轴混合展示所有来源请求，每行带 IP/项目 | 聚合全部来源的域名/路径树，叶子请求仍保留 IP/项目 |
| 单 IP | 仅展示指定来源的时间序列 | 同一来源的域名/路径树 |

“流式”指按请求开始时间持续追加的列表，不意味着首版新增 SSE/WebSocket 协议处理。“所有流量”指经过本代理的流量，不代表设备上绕过代理的网络请求。

建议默认进入全部 IP 流式视图；流量页有独立项目筛选，默认全部项目并包含未绑定来源，明确显示当前范围。其他页面的“查看项目”不暗中限制全部流量。本次会话记录保存请求当时的项目归属，设备改绑不能改写旧记录。这些范围默认值和历史边界见 D18。

建议目录层级为“协议 + 域名 + 端口 → 路径段 → 请求实例”；Query、方法、时间、IP 保留在实例中，不因为路径相同而去重。不同 IP 相同接口允许聚合，但不能丢失来源。同一筛选下两种视图使用同一批记录，切换保留筛选和选中请求。目录节点过滤后计数只统计当前查询范围，不能拿已加载一页冒充总量。

共用请求详情：概要、原始请求、修改后的请求、实际响应、耗时/错误、命中规则与规则集/步骤、实际配置版本。正文未保存、超限截断、HTTPS 未解密分别显示原因；随机结果查看实际输出，不重新生成。

建议提供搜索、IP/项目/域名/方法/状态/来源过滤、自动滚动开关和清空视图；自动滚动开关只控制跟随滚动，不停止代理或持久记录。D09 已确认重启不恢复本次流量，仅主动导出留存；清理会话缓存不能删除规则和已提取样本。缓存容量、正文限制与敏感字段处理仍由 D09 细化。

## 6. 旧规划如何清理

| 原内容 | 本轮处理 |
| --- | --- |
| 六工作区、七入口导航、Mock 与规则集合并页面 | 删除旧布局描述，替换为四模块；接口定义与编排分开 |
| 独立 Mock 组入口 | 合入规则集管理；保留既有顺序执行需求及运行设计 |
| 独立数据入口 | 合入规则管理的样本/业务数据辅助功能 |
| 项目配置里的通用 Header | 移到规则管理，项目作用域保留 |
| 应用设置里的证书入口 | 移到设备管理统一呈现，证书后端仍是应用级资源 |
| 随机响应、项目隔离、MCP、版本、存储与测试设计 | 保留既有范围；MCP 从公共设置进入，不新增业务模块 |
| 旧 UI 布局备选与重复页面地图 | 用四模块 UI 方案替换，避免并存两套执行依据 |

当前没有需要清理的业务代码或运行数据。技术专题仍有独立价值，保留文件；过时段落直接替换，不再新增一套历史规划参与执行。

## 7. 需要重点关注的遗漏

| 事项 | 为什么需要明确 | 决策入口 |
| --- | --- | --- |
| 编排是否包含顺序执行 | 优先级排序与逐步消费不是同一功能；本轮按保留旧能力归并入口 | D17 |
| 全部流量与项目边界 | 未绑定来源不应消失，改绑后历史不可串到新项目 | D18 |
| Header 生效范围 | 已确认项目通用 Header 适用于已绑定可处理 HTTP 流量；未绑定项目不改写，接口专用最后覆盖 | D20 已确认 |
| 多设备共用规则的影响 | 编辑/禁用/删除可能同时改变其他设备；需要引用和生效提示 | D06、D10、D19 |
| 证书重置与设备可信状态 | 下载成功不等于已安装信任；重建 CA 后可能需要重新安装 | D21 |
| IP 复用与设备恢复 | 新手机可能使用旧 IP；保留绑定可能沿用旧配置 | D07、D21 |
| 流量容量和清理 | 长期开启不能无限占内存/磁盘；列表可见与正文持久化不同 | D09、D12 |
| 在途请求与顺序并发 | 保存、改绑、重置不能使旧响应推进新运行 | D04—D06 |
| 协议与异常 | 首版 HTTP/HTTPS JSON；未解密和不支持正文需诚实显示 | 03 专题、D21 |
| 备份/导入导出 | 规则配置和流量记录分别考虑，不能混入私钥或运行控制 | D10、D11、D13 |

已确认仅目录式提供流量导出，首版不做流量导入；导出格式仍需细化。重发、延迟/故障注入继续作为待选补充，手动断点、跨步骤变量、团队服务不因“仿 Charles”自动加入首版。

## 8. 推进顺序与规划验收

用户本轮指定的主线为：功能分析 → 模块详细设计 → UI 设计 → 界面实现 → 测试用例编写。详细任务、产物和完成条件见 [五阶段推进计划](superpowers/plans/2026-09-10-project-delivery.md)。此顺序替代之前直接优先细化 UI 的安排；已有 UI 草案保留为分析材料。

1. 功能分析：四模块操作清单、用户流程、范围与验收条件，收口相关未决决策。
2. 模块详细设计：字段、数据关系、命令/查询、事件、错误与生效规则；复用既有技术专题。
3. UI 设计：四模块页面、状态、视觉规范与交互原型，对齐功能和接口。
4. 界面实现：公共壳到四模块及跨页流程；明确演示适配与真实核心联调状态，开发期间执行必要验证。
5. 测试用例编写：正式四模块及跨模块用例、需求覆盖、选定自动化脚本。用例写完不等于执行通过。

真实代理/证书、存储、MCP、双平台打包等支撑工作按 [技术实施顺序](design/10-testing-delivery.md) 管理依赖；不在页面中假装已完成。

规划验收：一级业务入口恰好四个；设备能找到实际配置和自己的流量；规则正文与编排只有各自统一编辑入口；流量四种组合不丢来源、不改变执行；每项旧能力有归属或明确延期决定；建议不标成用户已确认。

流量导出范围（D13 已确认）：仅目录式视图提供导出，流式视图不显示导出操作；首版不提供流量导入。文件格式与导出范围在详细交互中收口；D09 已确认重启不恢复流量，只有主动导出保留。

逐项功能与阶段协作见 [功能分析](functional-analysis.md)。用户已授权自主完成完整软件，关键行为、UI 定稿和真机测试按检查点协作；开发包括真实核心与回归打包，不能停在演示界面。

UI 评审决定 D22：运行控制属于设备，规则集页只编辑定义和查看关联设备，不直接开始/停止/重置。D23 已确认多关联、单个启用；界面布局通过不等于所有关联语义均已冻结。

关联模型 D23 已确认：设备 ↔ 规则集多对多；每设备同时至多启用一个。设备页区分已关联、本次候选、实际启用；启用/停止只影响本设备。规则集页展示关联设备的独立状态并跳转设备管理。
