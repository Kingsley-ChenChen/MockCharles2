# 04 请求匹配与 Header 规则

已确认：按修改前原始请求匹配；支持方法、域名、路径及 Query/Header/JSON Body 条件；独立模式第一条启用且匹配规则获胜。以下表达式细则是 D14 的审阅草案。

产品入口：接口规则与请求/响应 Header 定义在规则管理，接口规则优先顺序和步骤编排在规则集管理。Header 不因入口迁移自动新增规则集覆盖层；D20 已确认按项目统一生效、未绑定项目不改写 Header、接口专用最后覆盖；规则集不增加 Header 引用层。

## 1. 请求视图与编译

传输层构建不可变 OriginalRequestView。匹配器只读该视图，不读取通用 Header 修改后的请求。保存规则时编译表达式，错误定位到条件，不等请求到来才发现明显无效配置。

实现建议：请求方法规范成大写；域名按 DNS 语义比较并单独保存可选端口；Header 名称大小写不敏感，值不自动转小写；路径不偷偷解码两次，不把尾斜线当作相同路径。具体匹配选项应明确显示。

## 2. 匹配配置示例

```json
{
  "method": "POST",
  "host": "api.example.test",
  "path": { "kind": "exact", "value": "/orders/confirm" },
  "conditions": [
    { "source": "query", "key": "channel", "op": "equals", "value": "app" },
    { "source": "header", "key": "X-Env", "op": "equals", "value": "test" },
    { "source": "json", "pointer": "/order/type", "op": "equals", "value": "normal" }
  ]
}
```

示例仅表达保存结构，不代表全部操作符已确认。建议所有条件为 AND；需要 OR 时用多条规则表达。JSON 路径采用显式字段定位；数组通配、正则和路径参数模板应按 D14 决定，不用前端自由文本暗中扩展语法。

建议明确区分：字段不存在、字段为 null、空字符串、数字 1、字符串 "1"。对重复 Query/Header 值可配置 any/all，若首版只做 any 需用户确认。JSON 无法解析时有 JSON 条件的规则判为未匹配并记录原因，不能把不存在当成 null。

## 3. 规则选择

| 设备状态 | 候选与结果 |
| --- | --- |
| 真实转发 | 不选 Mock |
| 独立 Mock | 使用该设备选择的可复用规则集，按显式顺序检查启用规则，第一条命中即停止 |
| 顺序组且 running | 只检查当前有效步骤；命中选择其 Mock 响应 |
| 顺序组未开始/已完成/已停止 | 真实转发 |
| 顺序组当前步不匹配 | 真实转发；不扫描独立规则来替代 |

命中解释包含规则/步骤 ID、列表位置、每个已检查条件的结果。UI 可附加“可能属于后续步骤”诊断，但不能让诊断扫描改变执行决策或泄露尚未保存的配置。

## 4. Header 操作结构

建议以有序操作列表表达，不以普通单值 Map 存储：

```json
[
  { "name": "X-Env", "action": "set", "values": ["mock"] },
  { "name": "Authorization", "action": "remove" },
  { "name": "Set-Cookie", "action": "append", "values": ["debug=1; Path=/"] }
]
```

set 替换同名所有值，remove 删除同名所有值，append 增加独立值；输入校验拒绝换行注入。多条通用规则如何排序建议用显式 order，避免同时引入隐式“具体度”。

应用顺序：基础 Header → 适用通用操作 → 命中接口操作 → 协议必要规范化。最后一步只负责正文长度、编码及连接相关协议一致性；不可任意吞掉用户业务 Header。对于不能安全编辑的协议字段，编辑界面应直接校验并说明。

请求 Header 在真正透传时发给上游；命中完整 Mock 时不会为修改请求 Header 额外调用上游。界面仍可查看计划中的修改。响应 Header 对真实响应与 Mock 响应同样遵循上述顺序。

## 5. 版本边界（D06 已确认）

| 保存内容 | 生效边界 |
| --- | --- |
| 响应内容与随机配置 | 下一请求使用新版本 |
| 项目/接口 Header、独立规则匹配、独立启用、优先集合顺序 | 下一请求使用新版本 |
| 顺序运行的匹配条件、步骤顺序与步骤开关 | 下次开始/重置采用新快照 |
| 任何已选定计划的在途请求 | 保留已选完整版本，不混用新旧定义 |

组 matcher 存入顺序版本；编辑规则 matcher 不改变正在运行的组。响应仍通过稳定 mockId 在新请求时读取活动版本。保存接口按字段返回 next_request/next_run 的生效说明，不能一个混合保存按钮只标“立即生效”。

## 6. 边界验收

大小写不同的 Header 名仍能覆盖；多个 Set-Cookie 保持独立；原始 Header 符合条件但通用规则改掉后仍命中；第一条禁用后第二条可命中；组后续步骤请求真实转发；JSON 类型不匹配有明确解释；修改正文后长度/编码一致。
